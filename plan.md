# Implementation Plan — Self-Improving Patient Appointment Scheduling Agent

## File Structure

```
project/
├── main.py                          # Entry point: run eval loop, invoke improvement, repeat
├── agent.py                         # Single-turn agent loop (prompt + Groq LLM + tool dispatch)
├── tools.py                         # Tool definitions, mock implementations, configurable responses
├── guardrails.py                    # Pre-invocation guardrails (2 rules, applied before agent sees input)
├── state.py                         # SessionState dataclass: per-session dict + tool_call_log + transcript
├── evaluator.py                     # Runs all 8 scenarios, collects deterministic + judge verdicts
├── improver.py                      # Feeds failures to improve_prompt_template, writes new prompt version
├── judge.py                         # Sends transcript + question to judge model, parses JSON response
├── scenarios.py                     # Loads scenario definitions, drives scripted/simulated conversations
├── config.py                        # API keys, model names, retry config, file paths
├── prompts/
│   ├── v1_system_prompt.txt         # Initial agent system prompt (copied from v1_system_prompt.md)
│   ├── judge_prompt_template.txt    # Judge template (copied from judge_prompt_template.md)
│   ├── improve_prompt_template.txt  # Improver template (copied from improve_prompt_template.md)
│   └── v{n}_system_prompt.txt       # Auto-generated by improver.py for n >= 2
├── scenarios/
│   └── scenarios.yaml               # Machine-readable version of all 8 scenarios (from scenarios.md)
├── results/
│   └── v{n}_results.json            # Per-version: scenario verdicts, pass/fail, timestamps
└── README.md                        # Setup instructions, API key config, how to run
```

## Data Flow

```
┌─────────────────────────────────────────────────────────────────┐
│                        main.py loop                             │
│                                                                 │
│  for version in 1..MAX_ITERATIONS:                              │
│    1. Load prompts/v{version}_system_prompt.txt                 │
│    2. evaluator.py runs all 8 scenarios ──────────────────────┐ │
│       │                                                       │ │
│       │  Per scenario:                                        │ │
│       │   a. Create fresh SessionState                        │ │
│       │   b. If scripted: feed fixed user lines               │ │
│       │      If simulated: run simulated-patient LLM          │ │
│       │   c. For each user turn:                              │ │
│       │      i.  guardrails.py screens input                  │ │
│       │      ii. agent.py generates response + tool calls     │ │
│       │      iii. tools.py executes tools, updates state      │ │
│       │   d. Run deterministic checks on state + tool_call_log│ │
│       │   e. Send transcript to judge.py for LLM verdict      │ │
│       │   f. Combine into scenario result                     │ │
│       └───────────────────────────────────────────────────────┘ │
│    3. Save results to results/v{version}_results.json           │
│    4. If all scenarios pass → stop, declare success             │
│    5. Else: collect failing scenarios + diagnostics              │
│    6. improver.py generates v{version+1}_system_prompt.txt      │
│    7. Regression check: if new version regresses on previously  │
│       passing scenarios, revert and stop with warning            │
└─────────────────────────────────────────────────────────────────┘
```

## Implementation Order

Implement files in this order; each step depends only on prior steps.

| Step | File(s) | What to do |
|------|---------|------------|
| 1 | `config.py` | Define constants: model names, API key env var name, file paths, max turns per scenario (10), max improvement iterations (5). |
| 2 | `state.py` | Implement `SessionState` dataclass with fields: `availability_checked` (bool), `insurance_verified` (bool), `booked` (bool), `slot_id` (str\|None), `patient_id` (str\|None), `tool_call_log` (list of dicts: `{tool, args, result, index}`), `transcript` (list of dicts: `{role, content}`). Provide `reset()` and `to_dict()` methods. |
| 3 | `tools.py` | Implement 4 tool functions. Each takes `SessionState` + args, mutates state, appends to `tool_call_log`, returns a result dict. For eval, each tool accepts a `mock_config` dict that overrides its return value (so scenarios can inject `available=False` or raise exceptions). Implement `get_tool_schemas()` returning OpenAI-format function definitions for the 4 tools. |
| 4 | `guardrails.py` | Two functions: `check_booking_precondition(state) → (allowed: bool, message: str)` blocks `book_appointment` if `availability_checked` is False. `check_out_of_scope(user_message: str) → (blocked: bool, refusal_message: str)` uses keyword matching (list: "dose", "dosage", "prescri", "diagnos", "medication", "symptom", "treatment plan", "side effect") — returns a canned refusal if any match. No LLM call in guardrails. |
| 5 | `agent.py` | Single function `run_agent_turn(system_prompt, state, user_message, mock_configs) → agent_response`. Calls Groq chat completion with system prompt + transcript history + user message. Parses tool calls from response. For each tool call: check guardrails, execute tool, append result to transcript as tool role. Return final assistant text. Cap at 3 sequential tool calls per turn to prevent loops. |
| 6 | `scenarios.py` | Load `scenarios.yaml`. For scripted scenarios: return list of user messages. For simulated scenarios: call Groq with the sim-patient system prompt + conversation so far to generate next user message. Provide `run_scenario(scenario_def, system_prompt) → SessionState` that drives the full multi-turn conversation. |
| 7 | `judge.py` | `judge_scenario(transcript, question) → {"verdict": str, "justification": str}`. Renders judge template, calls Groq (llama-3.1-8b-instant), parses JSON from response. Fallback: regex for `"verdict"\s*:\s*"(yes|no|partial)"` if JSON parse fails; if regex also fails, return `{"verdict": "error", "justification": "Judge output unparseable"}`. |
| 8 | `evaluator.py` | `evaluate_all(system_prompt, scenario_defs) → list[ScenarioResult]`. For each scenario: run it, apply deterministic checks (defined per-scenario as Python lambdas or named functions), call judge, combine. `ScenarioResult`: `{scenario_id, deterministic_checks: dict[str, bool], judge_verdict, passed: bool}`. A scenario passes iff ALL deterministic checks are True AND judge verdict is "yes". |
| 9 | `improver.py` | `improve_prompt(current_prompt, failures) → new_prompt`. Renders improve template with current prompt + failure details. Calls Groq (llama-3.3-70b-versatile). Extracts new system prompt from response (look for the block between `===BEGIN REVISED SYSTEM PROMPT===` and `===END REVISED SYSTEM PROMPT===` markers). Writes to `prompts/v{n}_system_prompt.txt`. |
| 10 | `main.py` | Orchestration loop as shown in data flow. Load scenarios, run eval, check pass/fail, improve if needed, check regression, repeat. Print summary table after each iteration. |

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| **Deterministic checks for tool ordering; LLM judge for conversation quality** | Tool ordering (e.g., "was availability checked before booking?") is objectively verifiable from the log — using an LLM would add noise. Conversation quality (e.g., "did the agent offer alternatives?") requires language understanding. This split maximizes reliability. |
| **Exactly 4 tools** | These are the minimum set covering the core appointment lifecycle (check → verify → book → cancel). Adding more (e.g., list_appointments) would increase surface area without testing meaningfully different agent behaviors. |
| **Guardrail 1 (booking precondition) is code-level, not prompt-level** | Prompt-level "don't book without checking" is unreliable — the agent may ignore it under pressure (scenario 3). A hard code block makes the safety property invariant. The interesting eval question becomes: does the agent *handle* the block gracefully, not whether it *obeys* it. |
| **Guardrail 2 (out-of-scope) is keyword-based, pre-invocation** | Keeps medical-advice blocking deterministic and zero-latency. A false positive (blocking "I have a symptom of being late") is acceptable for a demo; production would use a classifier. Blocking before invocation means the agent never sees the request, preventing any chance of partial compliance. |
| **Simulated patient uses 8b-instant, not the 70b model** | Cost: simulated patient messages are the highest-volume LLM calls (one per turn per scenario). The patient doesn't need to be smart — it needs to follow a script with light adaptation. 8b is sufficient and stays within free tier limits. |
| **Regression gate before accepting a new prompt version** | Without this, the improver can fix scenario 6 by adding instructions that break scenario 1. The gate re-runs ALL scenarios and rejects the new prompt if any previously-passing scenario now fails. This makes the improvement loop monotonically non-regressing. |
| **Max 5 improvement iterations** | Prevents infinite loops if the prompt can't be fixed (e.g., a CodeBug). 5 iterations is enough to demonstrate the loop; the eval result at iteration 5 is the final submission regardless. |
| **Versioned prompt files on disk** | Enables post-hoc diffing (`diff v1_system_prompt.txt v3_system_prompt.txt`) to show exactly what the improvement loop changed. Also makes the system reproducible — re-running with a given version file produces the same results (modulo LLM non-determinism, mitigated by temperature=0). |
| **Temperature=0 for all LLM calls** | Maximizes reproducibility across runs. The agent, judge, patient sim, and improver all use temperature=0. |
| **10-turn cap per scenario** | Prevents runaway conversations (e.g., agent and sim-patient looping). If the scenario isn't resolved in 10 turns, it's marked as failed with a "timeout" note. |
